二、Spark 核心概念

一分鐘重點
  • RDD = 分散喺好多部機、唔可以改（immutable）嘅數據集合；壞咗靠 lineage 重新計。
  • Transformation（map、filter、flatMap、reduceByKey…）係 lazy，只係記低計劃；Action（collect、count、show、save）先真正執行。
  • 一變一用 map，一變多用 flatMap；加總用 reduceByKey，收集名單用 groupByKey。

Lazy evaluation：transformation 寫計劃，action 先開工

一句講完

Transformation 唔會即刻計，只係喺 memory 起一個 operator DAG；去到 action 先由頭到尾一次過執行。

圖解 點解要 lazy

等齊成個計劃先執行，Spark 可以合併步驟（pipelining）、避免計冇用嘅嘢；而且記低 lineage，有 partition 壞咗就照計劃重新計返嗰份。

易錯

MCQ 問「邊一行先真正執行」：搵第一個 action（collect、count、take、show、saveAsTextFile、write）。

map vs flatMap

一句講完

map：一個 element 變一個；flatMap：一個 element 變零至多個，再攤平成一個 RDD。

圖解
考試點揀

Mutual friends 每個 user 產生好多個 pair、inverted index 每份文件產生好多個 (word, doc)、PageRank 每頁產生好多個貢獻：全部用 flatMap。

reduceByKey vs groupByKey

一句講完

兩個都會按 key shuffle；reduceByKey 喺每個 partition 先合併一次再送，groupByKey 將所有 value 原封不動送過網絡。

Spark 係一個平行處理數據嘅框架，支援大規模處理、將數據放喺 memory、同埋喺 worker 之間分配資源。四個 feature：Fast processing（用 RDD）、In-memory computing、Flexible（Java、Scala、R、Python）、All-in-one（SQL、ML、可視化）。

Spark 架構（master–worker）

RDD（Resilient Distributed Dataset）

RDD 係乜

  • Spark 最基本嘅數據結構
  • Immutable：改唔到，只可以由舊 RDD 整個新 RDD
  • Distributed / partitioned：分成 partition，喺唔同機器平行處理
  • 只可以用 coarse-grained、deterministic 嘅 transformation 建立（map、filter、join）

三個關鍵特性

  • Lazy evaluation：唔即刻執行，只喺 memory 起一棵 operator tree，要結果先計
  • Lineage：記錄由原始數據到結果嘅每一步
  • Fault recovery：partition 失咗就用 lineage 重算；冇出事就冇額外成本

Transformation vs Action（必考）

Transformation（T）Action（A）
回傳新 RDD（RDD1 → RDD2）一個值或 Python list（RDD → output）
幾時執行Lazy：只記入 logical plan／lineage即刻觸發成條鏈執行
例子map flatMap filter distinct groupBy groupByKey reduceByKey mapValues sortBy sortByKey union intersection subtract cartesian join leftOuterJoin randomSplitcollect count first take sum mean min max stdev
陷阱

reduceByKey 個名有 reduce，但佢回傳 RDD，所以係 transformation。Lecture slide 29 將 parallelize 都當 transformation（“four operations in two types”：parallelize、map、filter 係 T，collect 係 A）。

Lazy 嘅證明：spark.textFile('不存在.txt') 唔會出錯，去到 .collect() 先報錯。好處：Spark 可以睇晒成條鏈先執行，合併同 pipeline 步驟、減少重複處理，慳時間同運算資源。

Slide 29–31 例子：data = [("A",1), ("B",2), ("A",3), ("B",5)]，先 map 乘 2 再 filter key == 'A'，得 [('A', 2), ('A', 6)]。調轉做（先 filter 再 map）結果一樣但更快，因為 map 要處理嘅數據少咗。

lambda 入面嘅 x 係乜？（老師話每次都要問自己）

寫法x／參數代表
spark.textFile(…).map(lambda x: …)一行文字（string）
.flatMap(lambda x: x.split()) 之後嘅 .map(lambda x: …)一粒字
key-value RDD 嘅 .map / .filter(lambda x: …)成個 tuple：x[0] = key，x[1] = value。value 都係 tuple 嘅話用 x[1][0]、x[1][1]
.mapValues(lambda v: …)淨係 value，唔使 index
.reduceByKey(lambda a, b: …)同一個 key 嘅兩個 value
.sortBy(lambda x: x[1])一個 tuple，按 x[1] 排
.groupByKey() 之後 .map(lambda x: …)x[0] = key，x[1] = ResultIterable（要 list()）
groupBy(lambda x: x % 2)每個元素；x % 2 嘅結果（0 或 1）會變成 key

Pair RDD 再加四個：mapValues、flatMapValues、countByKey、countByValue

一句講完

頭兩個係 transformation，只郁 value、key 唔變；後兩個係 action，即刻計，返回 Python dict（defaultdict），唔係 RDD。

Operator類型輸入 → 輸出
mapValues(lambda x: [x, x*10])Transformation(a, 1) → (a, [1, 10])：一個 element 變一個
flatMapValues(lambda x: [x, x*10])Transformation(a, 1) → (a, 1)、(a, 10)：list 攤平，每個 value 配返同一個 key
countByKey()Action → dict數每個 key 出現幾多次
countByValue()Action → dict數每個成個 element（成個 tuple）出現幾多次
圖解：mapValues vs flatMapValues（T4 4.1–4.2，mtcars）
例子：countByKey vs countByValue（T4 4.3）

carData = [(Mazda, 2018), (Mazda, 2019), (Ferrari, 2019), (Porsche, 2019)]

Call結果

carData.countByValue(){(Mazda, 2018): 1, (Mazda, 2019): 1, (Ferrari, 2019): 1, (Porsche, 2019): 1}

例子：汽車 = TF／DF 模板（T4 4.4）

(2018, 'Mazda Ferrari')、(2019, 'Porsche Ford Mazda')、(2020, 'Ferrari Honda Tesla Mazda')：

  • flatMapValues(lambda x: x).countByValue() → 每個 (year, brand) 出現幾次 = term frequency
  • flatMapValues(lambda x: x).distinct().map(lambda x: (x[1], x[0])).countByKey() → Mazda 3、Ferrari 2、其餘 1 = document frequency
  • count() → 3 = 文件數

易錯
  • Notebook 註解話 countByValue 係「每年出咗幾多架車」，係誤導：佢數成個 tuple，四個 tuple 各 1。
  • Slide／notebook 寫 flatMapValues「3 input will have 1 output」，係講錯：每個 input 變 2 個 output，3 個 input 就 6 個 output。
  • mapValues／flatMapValues 放喺 多欄 Row 上面（例如 mtcars 12 欄）：Spark 只當 x[0] 係 key、x[1] 係 value，其餘欄全部丟走。所以 mtcars 結果只有 (車款, [mpg, mpg×10])。
  • countByKey／countByValue 係 action，後面唔可以再 .map()；要繼續用 RDD 就改用 map((k, 1)).reduceByKey(add)。

四、Hive → Shark → Spark SQL、DataFrame

一分鐘重點
  • 點解要 Hive：MapReduce 只有兩段，複雜 query（例如每個 category top-2）要串幾個 job，join／sort 全部手寫，太 low-level。
  • Hive 將 SQL 變 MapReduce（慢）；Shark 用 Spark + memory（快）；Spark SQL 加 DataFrame + Catalyst optimizer。
  • DataFrame = 有 schema 嘅分散式 table；schema 用 StructType([StructField(name, type, nullable)])。
  • UDF = 自己寫嘅 Python function：udf(f, ReturnType)，return type 錯就出 null。

同一題三種寫法：每個 category 嘅 top-2 URL（Exam Review p.42–47、L4 p.6–13）

題目

兩個 table：Visits（User, URL, Time）同 UrlInfo（URL, Category, PageRank）。搵每個 category 最多人睇嘅 2 個 URL。

點解要串兩個 job

MapReduce 每個 job 只有 Map 同 Reduce 兩段，一次 shuffle 只可以按一種 key 分組。呢題要先按 URL 分組（join + 數 visit），再按 category 分組（排名），所以要兩個 job，第一個 job 嘅輸出寫落 HDFS 再俾第二個 job 讀。

寫法 ①：兩階段 MapReduce pseudocode

# ---------- Job 1：join Visits 同 UrlInfo，數每個 URL 嘅 visit ----------
Mapper1(user, url, time):            emit(url, ("visit", 1))
Mapper2(url, category, pagerank):    emit(url, ("info", category))
Reducer1(url, values):
    visit_count = 0; category = null
    for v in values:
        if v.type == "visit": visit_count += v.count
        if v.type == "info":  category = v.category
    if category != null and visit_count > 0:
        emit(category, (url, visit_count))

# ---------- Job 2：每個 category 排名，取頭 2 ----------
Mapper3(category, (url, count)):     emit(category, (url, count))
Reducer2(category, values):
    L = sort(values, by count, descending)
    for rank, (url, count) in enumerate(L[0:2], start=1):
        emit((category, rank), (url, count))

寫法 ②：點解話「MapReduce API too low-level」

上面兩個 job，join、select、projection、aggregate（count）、sort、distinct 全部要自己逐行寫。程式員其實只係想講「join 完 group by 再排名」。所以 Facebook 整咗 Hive：用 SQL 寫，Hive 自動 compile 成 MapReduce job（Facebook 超過 90% 嘅 MapReduce job 由 Hive 生成）。

寫法 ③：HiveQL 一句搞掂

SELECT category, url, visit_count, rank FROM (
    SELECT u.category, v.url, COUNT(*) AS visit_count,
           RANK() OVER (PARTITION BY u.category
                        ORDER BY COUNT(*) DESC, v.url ASC) AS rank
    FROM Visits v JOIN URLInfo u ON v.url = u.url
    GROUP BY u.category, v.url
) ranked
WHERE rank <= 2
ORDER BY category, rank;
SQL 部分對應 MapReduce
JOIN … ON v.url = u.url + GROUP BY + COUNT(*)Job 1（按 URL shuffle，join + 數）
RANK() OVER (PARTITION BY category ORDER BY … DESC)Job 2（按 category shuffle，排序）
WHERE rank <= 2Job 2 Reducer 嘅「取頭 2」

輸出同 MapReduce 版一樣：Ecommerce 1 amazon.com 2；Social Network 1 twitter.com 2、2 facebook.com 1；Sports 1 espn.com 1（已用 SQLite 跑過）。

易錯
  • Reduce 1 要分清兩種 value（"visit" 同 "info"），所以 mapper 要加 tag；冇 tag 就唔知邊個係 category。
  • Job 2 嘅 output key 係 (category, rank)，唔係 category。
  • PARTITION BY = 每個 category 各自排名；唔寫就變咗全部 URL 一齊排。
  • Slide 嘅 UrlInfo 表有兩個筆誤：twitter.com 嘅 category 印咗 “facebook.com”（Mapper 2 例子係 Social Network）、espn.com PageRank 一處寫 0.9 一處寫 0.6。唔影響答案（呢題唔用 PageRank）。

Hive

  • Facebook 開發，將 structure／schema 加落 HDFS 數據，將 HiveQL 編譯成 MapReduce jobs。當年 Facebook 超過 90% MapReduce job 由 Hive 產生。
  • HiveQL 係 limited 版 SQL：DDL（create／drop／alter table、database、view）、DML（insert、select、update、delete、load data）、query（SELECT / WHERE / GROUP BY / HAVING / ORDER BY / LIMIT、各種 JOIN）、functions、PARTITIONED BY、CLUSTERED BY（bucketing）。
  • LOAD DATA LOCAL INPATH ... OVERWRITE INTO TABLE t：LOCAL = 由本機讀；冇 LOCAL = 由 HDFS 讀；OVERWRITE = 刪走舊數據。Partitioned table 要寫 PARTITION (ds='2025-09-16')。
Hive 數據模型三層喺 HDFS 點樣存用途
Table每個 table 一個 directory，數據 serialize 成 file 放入去Typed columns（int、float、string、boolean），支援 map 類型
PartitionTable directory 入面嘅 sub-directory決定數據分佈，例如按日期 range-partition
BucketPartition directory 入面嘅 file（分 n 個 bucket 就 n 個 file）用 hash 再細分，方便 sampling 同 join

Hive 架構同編譯步驟

  • Metastore：存 table 嘅 schema、位置、partition 資料
  • Driver：管理 HiveQL query 嘅生命週期
  • Compiler：HiveQL → parse tree → plan
  • Execution engine：將 plan 變成 MapReduce 喺 Hadoop 執行

Parser（語法、parse tree）→ Semantic analysis（檢查 table／column／type）→ Logical plan generator → Optimizer → Physical plan generator（DAG of MapReduce jobs）

Hive 特點同限制

  • Petabyte 級 data warehouse，基於 MapReduce + HDFS；係 OLAP，唔係 OLTP
  • Fault-tolerant、scale-out、支援 nested data、UDF、custom mapper／reducer、SerDe
  • 限制：高 latency（細 query 都要幾分鐘）、唔啱互動式分析、多 join 嘅複雜 query 慢、冇內置 ML／iterative algorithm

Shark

  • 動機：data warehouse 有好強嘅 temporal locality（最近用過嘅數據好快會再用），Facebook 90% query 可以喺 main memory 完成。大部分 query 只睇細嘅數據 window（例如每日 log），唔使將 petabyte 塞入 memory。
  • 做法：保留 Hive 嘅 scalability 同 extensibility，將 Hive 嘅 MapReduce physical plan／execution engine 換成 Spark RDD，加 cache manager 同改 optimizer。

from pyspark.sql import SparkSession
ss = SparkSession.builder.appName("InvertedIndex").master("local[4]").getOrCreate()
spark = ss.sparkContext

lines = spark.textFile("documents.txt")
docs = lines.map(lambda l: l.split("||")) \
            .map(lambda p: (p[0].strip(), p[1].strip().split()))   # (doc_id, [words])

index = docs.flatMap(lambda d: [(w, d[0]) for w in set(d[1])]) \
            .groupByKey() \
            .mapValues(lambda ids: sorted(set(ids))) \
            .sortByKey()

for word, ids in index.collect():
    print(f"{word}: {ids}")
步驟點解
split("||") + strip()分開 doc id 同內容，去走空格
flatMap + set(d[1])一份文件產生好多個 (word, doc)；set 令 D1 嘅兩個 “the” 只出一次
groupByKey()同一個字嘅 doc id 收埋一齊
mapValues(sorted(set()))轉做 list、去重、排序
sortByKey()字按字母排，同 expected output 一樣

都可以用 reduceByKey(lambda a, b: a + b)，map 嗰陣 value 寫 [doc_id]。已用 Python 模擬核對：the → ['D1', 'D3', 'D4']、brown → ['D2', 'D3', 'D4']。

Compliance risk UDF：回傳 nested struct 再 flatten

from pyspark.sql.functions import udf, col
from pyspark.sql.types import StructType, StructField, StringType, IntegerType, ArrayType

def evaluate_compliance_risk(memo, country):
    if memo is None or str(memo).strip() == "":
        return {"risk_score": -1, "flagged_terms": []}
    memo_lower = str(memo).lower()
    country_upper = str(country).upper() if country else ""
    crypto_terms = {"crypto", "bitcoin", "mixer"}
    urgency_terms = {"urgent", "gift", "loan"}
    found_terms = [t for t in crypto_terms | urgency_terms if t in memo_lower]
    score = 0
    if any(t in memo_lower for t in crypto_terms):
        score += 50
    if any(t in memo_lower for t in urgency_terms) and country_upper != "US":
        score += 30
    score = min(score, 100)
    return {"risk_score": score, "flagged_terms": found_terms}

compliance_schema = StructType([
    StructField("risk_score", IntegerType(), False),
    StructField("flagged_terms", ArrayType(StringType()), False)
])

compliance_udf = udf(evaluate_compliance_risk, compliance_schema)

df_temp = df_transactions.withColumn(
    "audit_result", compliance_udf(col("memo_text"), col("account_country")))

df_audited = df_temp.select(
    col("transaction_id"), col("account_country"), col("memo_text"),
    col("audit_result.risk_score").alias("audit_score"),
    col("audit_result.flagged_terms").alias("triggered_keywords"))
  • Dict 嘅 key 一定要同 StructField 名一樣，否則對唔上，出 null。
  • ArrayType(StringType()) = 裝字串嘅 list。
  • 傳 column 嘅次序要跟 function 參數：先 memo，後 country。
  • 用 "struct.field" 攞出 nested 欄位，再 .alias() 改名。

九、短答題

1. Transformation vs action；乜嘢係 lazy evaluation，有咩好處？

A transformation (e.g. map, filter, reduceByKey) creates a new RDD from an existing one. It is lazy: Spark only records it in the lineage / logical plan and does not execute it. An action (e.g. collect, count, take) returns a value to the driver and triggers the execution of all pending transformations. Lazy evaluation lets Spark see the whole chain first, so it can optimise it (merge and pipeline steps, skip unnecessary work), saving time and computing resources.

2. Narrow vs wide transformation，各舉一例；點解 wide 貴啲？

In a narrow transformation, each output partition is computed from a single input partition (e.g. map, filter), so no data needs to move between workers. In a wide transformation, an output partition needs data from many input partitions (e.g. groupByKey, reduceByKey, sortBy, join), so data must be shuffled across the network. The shuffle adds network I/O and latency and starts a new stage, so wide transformations are more expensive.

3. 點解 Spark 通常比 Hadoop MapReduce 快，尤其係 iterative job？

MapReduce writes all intermediate results to disk (with replication) and can only share data between jobs or iterations through shared storage, so every iteration pays disk I/O. Spark keeps RDDs in memory (and can cache RDDs that are reused), chains many transformations in one job, and gets fault tolerance from lineage instead of replicating intermediate data.

4. RDD 點做到 fault tolerance？worker 死同 driver 死有咩分別？

RDDs are immutable and remember their lineage, the deterministic transformations used to build them from the original data. If a worker fails, its lost partitions are recomputed from the original data using the lineage, and the driver reassigns the tasks to other workers, so the job continues. If the driver fails, the application's state is lost; there is no automatic recovery, so the application must be restarted from the beginning.

6. map() 同 flatMap() 有咩分別？

map() produces exactly one output element for each input element, so splitting sentences gives one list per sentence (nested lists). flatMap() lets each input produce zero or more outputs and flattens them, so splitting sentences gives one flat RDD of words. Example: ['hello world', 'hi'] → map gives [['hello','world'], ['hi']]; flatMap gives ['hello','world','hi'].

1. 點解 DataFrame 通常比 RDD 快？

A DataFrame has a schema (named, typed columns), so Spark knows the structure of the data and the operations are declarative. The Catalyst optimizer can rewrite the logical plan (predicate pushdown, constant folding, join reordering, runtime code generation) and data is stored in a compact columnar binary format. RDD transformations take arbitrary lambdas that are black boxes to Spark, and the data are opaque Java/Python objects, so little optimization is possible.

2. 點解 Hive 慢？Shark 點改善？

Hive compiles HiveQL into MapReduce jobs, which write intermediate results to disk, so even small queries take minutes and it is unsuitable for interactive or iterative analytics. Shark keeps HiveQL compatibility but replaces the MapReduce execution engine with Spark RDDs, exploiting temporal locality with in-memory table caching, columnar memory storage, data co-partitioning and Partial DAG Execution that re-optimizes the plan at run time.

3. 點解 Shark 被 Spark SQL 取代？

Shark could only query external data in the Hive metastore, not data inside Spark programs; it had to be invoked through SQL strings, which is error-prone; and it inherited Hive's optimizer designed for MapReduce, which was hard to extend. Spark SQL adds the DataFrame API that mixes SQL with programmatic code and the extensible Catalyst optimizer.

9. (5 marks) Define lazy evaluation in Spark DataFrames. Use an example to justify your answer.

Lazy evaluation means operations are not executed when they are written; Spark only records them as a logical plan and runs them when an output operation needs a result. For example, df.filter(df.quantity > 20).withColumn("revenue", df.quantity * df.price) reads no data; Spark only builds a plan with a filter and a new column. When .show() or .count() is called, the Catalyst optimizer optimizes the whole plan (e.g. pushes the filter down so fewer rows are processed) and then executes it on the workers.

10. (5 marks) What is a user-defined function (UDF) in Spark SQL, and why must its return type be declared?

A UDF wraps a normal Python function so it can be applied to DataFrame columns when built-in Spark SQL functions are not enough, e.g. classifying unstructured review text. It has two parts, the function and the output data type, as in sentiment_udf = udf(analyze_sentiment, StringType()), applied with withColumn("sentiment_category", sentiment_udf(col("feedback_text"))). Because a DataFrame has a schema, Spark must know the type of the new column in advance; if the declared type does not match the returned values, the column becomes null. A UDF is a black box to the Catalyst optimizer, so built-in functions such as when are preferred when they can do the job.

十、常見疑問

Q：RDD 同 DataFrame 有咩分別？
RDD 係最底層嘅分散式 collection，冇 schema，Spark 睇唔到你 lambda 入面做咩，所以冇得優化。DataFrame 有 schema（column 名同 type），Catalyst optimizer 可以自動優化，通常快啲。
Q：SparkSession 同 SparkContext 點分？
SparkContext（題目通常叫 spark 或者 sc）係 RDD 嘅入口；SparkSession 係 DataFrame／SQL 嘅入口，入面包住一個 SparkContext（ss.sparkContext）。2025s1 卷寫 spark = ss.sparkContext，所以嗰張卷 spark.textFile 係 RDD。
Q：groupByKey 同 reduceByKey 點揀？
要「收集名單」用 groupByKey；要「加總／計數／搵最大」用 reduceByKey，因為佢會先喺每個 partition 合併，shuffle 少好多。
Q：col 係咪改名？
唔係。col("x") 係「揀出 x 呢個 column」；改名用 .alias()；withColumn 第一個參數係新 column 嘅名。
Q：countByKey 同 reduceByKey 有咩分別？
結果一樣係「每個 key 幾多次」，但 countByKey 係 action，即刻返回 Python dict 去 driver；map(lambda x: (x[0], 1)).reduceByKey(add) 係 transformation，結果仲係 RDD，可以再 join（T5 TF-IDF 就係咁做）。
Q：Top-2 per category 考 pseudocode 要寫幾多？
兩個 job 各寫 Map 同 Reduce，寫清楚 emit 乜 key、乜 value；Job 1 mapper 要加 "visit"／"info" tag；Job 2 reducer sort desc 取頭 2，emit ((category, rank), (URL, count))。
Q：唔識 list comprehension 點算？
用普通 for loop 加 append 一樣得分，例如 mutual friends 嘅雙重 loop。
Q：UDF return type 寫錯會點？
唔會報錯，個 column 會變 null。所以 schema／return type 一定要同實際回傳嘅嘢夾。
